02

Volumes & persistence

A database is only useful if committed data survives. Here’s what you proved with your own experiments.

Experiment A: no volume named

  1. You started Postgres without -v and created an orders table.
  2. docker inspect showed a volume anyway, with a long random name. The postgres image declares its data folder as a volume, so Docker quietly created an anonymous volume.
  3. You deleted the container and started a new one, and got relation "orders" does not exist.
  4. docker volume ls showed two volumes: the old one (your data, still there) and a new empty one for the new container.

The data wasn’t deleted, it was orphaned: still on disk, but nothing points to it. In real systems the disk fills with copies and nobody knows which one is the real database.

Experiment B: a named volume

docker run -d --name scratomus -v scratomusdata:/var/lib/postgresql -e POSTGRES_PASSWORD=pw postgres:18

You deleted the container, started a differently named container with the same -v, and AAPL was still there. The data belongs to the volume, not the container.

The -v flag

-v VOLUME_NAME:PATH_INSIDE_CONTAINER
  • Left side: a name you choose. If the volume doesn’t exist yet, Docker creates it.
  • Right side: the folder where the program writes its data. It has to be exactly right.

How to find the right path

  1. Ask the image: docker image inspect postgres:18 --format '{{json .Config.Volumes}}'
  2. Read the image’s Docker Hub page (the PGDATA section for Postgres).
  3. Look at the Destination in docker inspect of a running container.
Version trap

Postgres 18+ uses /var/lib/postgresql. Postgres 17 and older used /var/lib/postgresql/data, and most tutorials still show the old path.

Why a wrong path is dangerous

If you mount your named volume at the wrong folder, Postgres writes somewhere else (into an anonymous volume), and your named volume stays empty. There’s no error and everything appears to work. You only find out when the container is re-created and the database is empty, often during a demo or in production. It fails silently.

Docker Compose

Instead of typing long docker run commands, you describe your containers once in compose.yaml and start them all with one command.

Your finished file

services:
  db:                                   # a service = one kind of container
    image: postgres:18
    environment:
      POSTGRES_USER: engine
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}  # value comes from .env
      POSTGRES_DB: engine               # the database name you connect to
    ports:
      - "127.0.0.1:5432:5432"           # only this machine can connect

      test: ["CMD-SHELL", "pg_isready -U engine -d engine"]
      interval: 5s
      timeout: 3s
      retries: 10

  pgdata:                               # ② declare: just the name

The two volumes: sections

① Inside the service

“Mount this volume at this path.” Written as - name:path.

② At the top level

“These named volumes exist.” Only the name, followed by a colon.

Analogy

② is the building’s list of filing cabinets. ① is the instruction “put cabinet X in this desk’s Data drawer”.

YAML rules

  • key: value, with a space after the colon.
  • Indent with 2 spaces, never tabs. Indentation shows what belongs to what.
  • A list item is - item, with a dash and a space.
  • Wrap port mappings in quotes. Older YAML can misread numbers with colons, such as 22:22.

Reading Compose errors

ErrorWhat it means
services.db.volumes must be a arrayMissing space after a dash, so YAML didn’t see a list item.
additional properties 'X' not allowedSomething is in the wrong place. If no path appears before it, the problem is at the top level.

Health check: running isn’t the same as ready

For a few seconds after starting, Postgres is running but not yet accepting connections. The health check runs pg_isready every 5 seconds. docker compose ps shows (health: starting) first, then (healthy). Later, your workers will wait for healthy before they start.

Don’t mix these up

The volume answers “does the data survive?”, and the health check answers “is the database ready right now?”. A health check has nothing to do with saving data.

04

Secrets & ports

The password lives in .env

  • .env holds POSTGRES_PASSWORD=… and stays on the server.
  • compose.yaml only contains the placeholder ${POSTGRES_PASSWORD}, so it’s safe to put on GitHub.
  • .gitignore lists .env and .venv, so Git never uploads them. This is the mechanism to name in an interview.

Postgres only reads POSTGRES_PASSWORD the first time it starts with an empty volume. After that, the password is stored inside the database, and changing .env does nothing.

Why 127.0.0.1

"5432:5432"

Published on every network interface. Any device on your WiFi or Tailscale can try passwords.

"127.0.0.1:5432:5432"

Only programs on the server itself can connect. That’s all your workers need.

Why ufw doesn’t help

Docker adds its own firewall rules for published ports, and they’re applied before ufw’s rules. So a ufw “deny 5432” never gets a chance to block the traffic. Remember: Docker’s rules come first.

Access from your PC: Tailscale can’t reach Postgres directly. You SSH into the server (over Tailscale), and an SSH tunnel (VS Code port forwarding) reaches localhost:5432. Expose as little as possible, and tunnel in when you need access.

06

SQL & CRUD

A table is a spreadsheet with strict rules: fixed columns, each with a type that refuses the wrong kind of data.

Your orders table

CREATE TABLE orders (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    symbol  text NOT NULL,
    side    text NOT NULL,
    qty     integer NOT NULL
);
PieceMeaning
bigintA whole number with a very large range.
GENERATED ALWAYS AS IDENTITYPostgres picks the id automatically (1, 2, 3…) from a sequence called orders_id_seq.
PRIMARY KEYUniquely identifies each row. No two rows can share an id.
text / integerText of any length / a whole number.
NOT NULLThe column must have a value.

The four CRUD commands

-- Create: add rows (Postgres fills in the id)
INSERT INTO orders (symbol, side, qty) VALUES ('AAPL', 'buy', 10);
INSERT INTO orders (symbol, side, qty) VALUES ('TSLA', 'sell', 5), ('MSFT', 'buy', 20);

-- Read: look at rows
SELECT * FROM orders;
SELECT * FROM orders WHERE side = 'buy';
SELECT symbol, qty FROM orders WHERE qty >= 10 ORDER BY id;
SELECT count(*) FROM orders;

-- Update: change rows
UPDATE orders SET symbol = 'AAPL' WHERE id = 1;

-- Delete: remove rows
DELETE FROM orders WHERE id = 2;

The shape of each command

CommandPattern
INSERTINSERT INTO table (cols) VALUES (vals); Use VALUES, not =.
SELECTSELECT columns FROM table WHERE condition ORDER BY col; What goes before FROM, where from goes after.
UPDATEUPDATE table SET column = new_value WHERE condition; Column on the left.
DELETEDELETE FROM table WHERE condition;

Quotes: the rule that catches everyone

'single' = a value

'AAPL' is a piece of text.

"double" = a name

"AAPL" means a column called AAPL, so you get column "AAPL" does not exist.

Single quotes are for strings. Write numbers without quotes: 5, not '5'.

UPDATE or DELETE without WHERE

This changes every row, with no warning. To protect yourself: (1) run a SELECT with the same WHERE first, to see which rows would change; (2) wrap risky changes in BEGIN … ROLLBACK/COMMIT.

Ids identify rows; they don’t count them

The sequence only moves forward. Deleted rows leave gaps (TSLA’s id 2 is gone forever), and even failed inserts use up an id (the rejected qty-0 order took id 8). This stops old references from pointing at the wrong order, and it’s fast when many workers insert at once. To count orders, use count(*).

Row order isn’t guaranteed

Without ORDER BY, Postgres returns rows in whatever order is fastest. Order 1 came out last because each UPDATE writes a new version of the row (MVCC). If the order matters, always use ORDER BY.

07

Constraints

Types catch the wrong kind of data. Constraints catch wrong values: −5 shares, a side of “banana”.

ALTER TABLE orders ADD CONSTRAINT qty_positive CHECK (qty > 0);
ALTER TABLE orders ADD CONSTRAINT side_valid  CHECK (side IN ('buy', 'sell'));
ALTER TABLE orders RENAME CONSTRAINT old_name TO new_name;
  • Why in the database and not only in Python: many writers (workers, API, signal generator) are protected by one rule, and it can’t be skipped by a bug.
  • Postgres checks existing rows first. If any row breaks the rule, it refuses to add the constraint (is violated by some row). A guarantee with exceptions isn’t a guarantee.
  • Name constraints clearly. The name appears in errors: violates check constraint "qty_positive".
  • In Python, a violation raises an exception (psycopg.errors.CheckViolation), so the bug is loud instead of silent.
Analogy

Python checks are the bouncer at the door. A constraint is the locked vault.

08

Transactions

A transaction groups several statements into one unit: all of them happen, or none do.

BEGIN;                         -- start (prompt becomes engine=*#)
UPDATE orders SET qty = 999;   -- you see 999…
ROLLBACK;                      -- …and it's undone: back to 10, 20, 3

BEGIN;
UPDATE orders SET qty = 50 WHERE id = 1;
COMMIT;                        -- permanent
SituationResult
Changes after BEGIN, then ROLLBACKAll undone.
Anything already COMMITtedPermanent. ROLLBACK can never undo it.
Worker crashes before COMMITPostgres notices the dropped connection and rolls back automatically.
Statement without BEGINAutocommit: it’s its own transaction, committed straight away.
DDIA · Ch. 7 · ACID

Atomicity: all or nothing. Kleppmann says it would be better named “abortability”. Durability: once COMMIT returns, the data survives crashes and power loss.

Analogy

A bank transfer: “take ₹500 from A” and “add ₹500 to B” must happen together, or the money disappears.

09

Isolation & locks

What happens when two connections touch the same data at the same time? You tested it with two terminals.

Experiment: who can see uncommitted changes?

Terminal A ran BEGIN; UPDATE … qty = 50. Terminal B still saw 10. After A’s COMMIT, B saw 50.

Experiment: both update the same row

A updated order 1 to 60 without committing. B’s update to 70 froze. It waited for A’s row lock. The moment A committed, B continued, and the final value was 70: the last writer wins.

DDIA · Ch. 7 · Read Committed (Postgres’s default)

No dirty reads: you never see another transaction’s uncommitted data.
No dirty writes: you can’t overwrite uncommitted data; you wait for its row lock.

  • Locks are on rows, not tables. Workers only wait when they touch the same row.
  • Locks are held until COMMIT or ROLLBACK, so keep transactions short.
  • A plain SELECT takes no lock.
  • MVCC: an UPDATE writes a new version of the row. That’s how B could keep reading the old committed version while A worked.

The lost update

The bug your whole engine exists to prevent. You caused it yourself.

Read-modify-write

with psycopg.connect(url) as conn:
    qty = conn.execute("SELECT qty FROM orders WHERE id = 1").fetchone()[0]   # 1. read
    time.sleep(5)
    new_qty = qty + 10                                                        # 2. modify in Python
    conn.execute("UPDATE orders SET qty = %s WHERE id = 1", (new_qty,))       # 3. write

Two scripts ran at once:

          Script A               Script B              DB qty
t=0s      read 80                                        80
t=1s                             read 80                 80
t=5s      write 80+10 = 90                               90
t=6s                             write 80+10 = 90        90   ← A's +10 is lost

It should have been 100. B calculated from a value that was already out of date. The plain SELECT took no lock, so both scripts read 80.

DDIA · Ch. 7 · Preventing lost updates

Read Committed does not prevent lost updates. You need an atomic operation or explicit locking.

In your engine

Replace “+10” with “status is pending → call Alpaca → mark done”. If two workers both read pending, both send the order, and you buy twice.

Fix 1: atomic update Tested ✓

UPDATE orders SET qty = qty + 10 WHERE id = 1

The maths happens inside Postgres, under the row lock, with no gap between read and write. Your two-terminal result: 90 → 110, so both additions counted.

Fix 2: SELECT … FOR UPDATE Tested ✓

SELECT qty FROM orders WHERE id = 1 FOR UPDATE

Used when the decision needs Python logic or a broker call, which can’t fit into one UPDATE. The read takes the row lock immediately, so a second worker waits until the first commits. Your result: A read 110 and wrote 120; B waited, read 120 and wrote 130.

A: SELECT … FOR UPDATE → 110   🔒 lock taken at the read
B: SELECT … FOR UPDATE         ⏳ waits; can't read yet
A: UPDATE to 120, COMMIT       🔓 lock released
B:                     → 120   ← reads the NEW value
B: UPDATE to 130, COMMIT
QuestionAnswer
How long is the lock held?Until COMMIT or ROLLBACK, not just while the SELECT runs. A 30-second Alpaca call means at least 30 seconds of lock.
Does a plain SELECT wait for it?No. It reads the last committed value straight away (MVCC). Locks only block other lockers: UPDATE, DELETE, FOR UPDATE. You tested this.
So what’s the danger?FOR UPDATE only protects you if every worker uses it. One plain SELECT walks past the lock, sees pending, and buys twice.
Atomic UPDATE or FOR UPDATE?Atomic when the change fits in one SQL statement; FOR UPDATE when Python must read, decide and act.
Next problem

With five workers all going for the same row, four sit waiting while other orders are ready. SKIP LOCKED says “if it’s locked, skip it and take the next one”. That’s Topic 5.

Analogy

Without FOR UPDATE, two people read the last page of a shared notebook and both write on it. With it, you take the notebook while you read, and the other person waits.

12

The job queue: SKIP LOCKED

A producer puts orders on a rail, and many workers take them off, each one exactly once, without waiting for each other. This is the core of the engine.

Analogy

A restaurant kitchen. Order tickets hang on a rail. Each cook takes the oldest free ticket, cooks it, and spikes it as done. Nobody hands out tickets: every cook checks the rail for themselves. A ticket a cook is holding is invisible to the others.

signal_generator ──(1 order/sec)──▶ [ rail: status = 'pending' ] ◀── worker 1
                                                                 ◀── worker 2
            pending  ──▶  processing  ──▶  done
          (on the rail)  (a cook has it)  (spiked)

Step 1 · A status column

ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'pending';
PieceMeaning
ALTER TABLEChange the structure of an existing table.
NOT NULLEvery row must have a value.
DEFAULT 'pending'Used for new INSERTs that don’t give a status, and written into every row that already exists. That’s why NOT NULL didn’t fail on AAPL, MSFT and NVDA.

You typed satus. Postgres doesn’t spell-check names, so it created that column happily. The fix keeps the data:

ALTER TABLE orders RENAME COLUMN satus TO status;

Step 2 · Allow only real statuses

ALTER TABLE orders ADD CONSTRAINT status_valid
  CHECK (status IN ('pending', 'processing', 'done'));

Without it, a typo like 'finsihed' would be stored, and no worker looking for 'done' would ever see that row. You predicted 'finished' would be written. It wasn’t:

ERROR:  new row for relation "orders" violates check constraint "status_valid"
DETAIL:  Failing row contains (1, AAPL, buy, 130, finished).
PartMeaning
new rowAn UPDATE writes a new version of the row (MVCC). Postgres checks that version before saving it.
relationPostgres’s word for a table.
"status_valid"Which rule broke. Good constraint names make errors readable.
ResultThe whole UPDATE was refused; AAPL stayed pending.

Step 3 · Claiming a job: FOR UPDATE vs SKIP LOCKED Tested ✓

BEGIN;
SELECT id, symbol FROM orders
WHERE status = 'pending'    -- only tickets on the rail
ORDER BY id                 -- oldest first
LIMIT 1                     -- just one
FOR UPDATE SKIP LOCKED;     -- lock it; rows others have locked are invisible to me
Terminals (each did BEGIN first)FOR UPDATEFOR UPDATE SKIP LOCKED
A claimsAAPLAAPL
B claims⏳ freezes until A commits/rolls backMSFT, instantly
C claims⏳ freezes tooNVDA, instantly
D (all 3 rows locked)⏳ freezes(0 rows), instantly. It doesn’t wait or go back to id 1.

Why not plain FOR UPDATE? With 5 workers, worker 1 holds AAPL for a 3-second Alpaca call while workers 2–5 all queue up behind it, so only one is ever busy. SKIP LOCKED keeps every worker busy at the same time.

Your first try: both got AAPL

Terminal A wasn’t inside a transaction. Without BEGIN, psql autocommits, so the lock was taken and released the instant the SELECT finished. A lock only lives as long as its transaction. Check the prompt: engine=# means no transaction, and engine=*# means you’re inside one and holding locks.

Forgotten transactions hold locks forever

The next morning, your three terminals from the day before were still idle in transaction, so they were still locking all three rows. A worker started then would have seen (0 rows) forever and you wouldn’t have known why.

-- who is connected, and what are they doing?
SELECT pid, state FROM pg_stat_activity WHERE datname = 'engine';

-- kill the stuck ones (a killed connection = automatic ROLLBACK, nothing lost)
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
WHERE state = 'idle in transaction' AND datname = 'engine';

It returned t three times, once for each killed session. The orders were still pending: those sessions had only locked the rows, and they hadn’t changed anything. Production databases set idle_in_transaction_session_timeout so this cleanup happens automatically.

Step 4 & 6 · worker.py

with psycopg.connect(url) as conn:
    while True:
        row = conn.execute("""
            SELECT id, symbol FROM orders
            WHERE status = 'pending'
            ORDER BY id
            LIMIT 1
            FOR UPDATE SKIP LOCKED
        """).fetchone()                  # a tuple, or None if 0 rows

        if row is None:
            conn.commit()                # close the empty transaction
            print("nothing to do")
            time.sleep(1)
            continue                     # back to the top of the loop

        order_id, symbol = row           # unpack (66, 'TSLA')
        print("claimed", order_id, symbol)
        time.sleep(2)                    # pretend: send to Alpaca
        conn.execute("UPDATE orders SET status = 'done' WHERE id = %s", (order_id,))
        conn.commit()                    # save 'done' AND release the lock
        print("done", order_id)
QuestionAnswer
Why 'pending' in single quotes?Without quotes, SQL treats pending as a column name: column "pending" does not exist. In double quotes it’s also a column name. Values always go in single quotes.
Why os.environ["…"] and not .get()?.get quietly returns None if .env is missing, which gives a confusing auth error later. [...] fails loudly with KeyError. In an engine, fail loudly.
Why commit when the rail is empty? There’s nothing to save.psycopg runs BEGIN before the first query, even a SELECT. The commit isn’t saving anything; it’s closing the transaction. Otherwise it stays open for hours (idle in transaction), blocks MVCC cleanup (bloat) and can be killed by timeouts. rollback() would do the same thing here. Think of an open bar tab with nothing ordered: you still close it.
Why commit after the UPDATE?It makes done permanent and releases the row lock. Rule: one job = one transaction.
During the 2-second sleep, what does a plain SELECT show?pending. You predicted done. The UPDATE hasn’t even run yet, and even after it runs, readers only see committed data.
Who wakes a sleeping worker when a new order arrives?Nobody. It wakes itself on a timer and checks again. This is polling (a pull model). Whichever worker checks first gets the order. If a worker dies, the others simply keep pulling. (LISTEN/NOTIFY can add a “wake up” signal later.)
Running on Linux: how do I start it?.venv/bin/python worker.py, or source .venv/bin/activate first. .venv\bin\activate is Windows style; on Linux the backslashes simply disappear.

Step 5 · signal_generator.py: commit first, then announce Tested ✓

SYMBOLS = ["AAPL", "MSFT", "NVDA", "TSLA", "AMZN"]

Without conn.commit():
  BEGIN ─ INSERT ─ INSERT ─ … 15 inserts … ─ Ctrl+C 💥 ─ ROLLBACK
  psql saw:        nothing (uncommitted)
  after Ctrl+C:    nothing (rolled back), and ids 5–19 burned forever
  the prints:      lied. "new order" appeared 15 times, and none were saved.

With conn.commit() after each INSERT:
  visible to workers immediately, survives Ctrl+C, first new id = 20
Rule

“I ran the INSERT” is not the same as “it’s saved”. It’s saved once it’s committed. And put the commit before the log line, so your logs never claim something the database doesn’t have.

Interview answers

Try each one out loud before opening it.

Your database runs in Docker. How do orders survive a container restart, and who can connect?

“Postgres stores its data on a named Docker volume mounted at its data directory, so I can destroy and re-create the container without losing anything. I publish the port only on 127.0.0.1, because Docker’s port rules bypass ufw, so a plain 5432:5432 would expose the database to the whole network. If I need access from another machine, I use an SSH tunnel instead of opening the port.”

What’s the difference between an image and a container?

“An image is a read-only template; a container is a running instance of it. One image can start many identical containers, which is how I’ll run several workers.”

Why is mounting a volume at the wrong path dangerous?

“It fails silently. The app writes to its real data directory, not the volume, so the volume stays empty. Everything works until the container is re-created, and then the data is gone.”

Why put constraints in the database if Python already validates?

“Many writers share one table, and a constraint protects all of them and can’t be skipped by a bug. A violation raises an exception, so bad data is loud instead of silently stored.”

What happens if a worker crashes in the middle of a transaction?

“Nothing it wrote is kept. Postgres sees the connection drop and rolls back the open transaction, so there’s never half-finished state. Anything committed earlier stays, because commits are durable.”

What is a dirty read? Does Postgres allow it?

“Reading another transaction’s uncommitted data. Postgres’s default, Read Committed, never allows it. It also prevents dirty writes: a second writer waits for the first one’s row lock.”

What is a lost update, and how do you prevent it?

“Two transactions read the same value, both modify it in application code, and the second write overwrites the first, so one change disappears. Read Committed doesn’t stop it. Fix it with an atomic update like SET qty = qty + 10 when the logic fits in SQL, or SELECT … FOR UPDATE to lock the row at read time when it doesn’t.”

Why are there gaps in the ids?

“Identity columns use a sequence that only moves forward. (In Topic 5, 15 rolled-back inserts burned ids 5–19, so the next order got id 20.) Deletes and even failed inserts consume numbers. That avoids reusing an id that something might still reference, and lets concurrent inserts proceed without coordination. Ids identify rows; count(*) counts them.”

Topic 5 · The job queue

How would you build a job queue in Postgres?

“A table of jobs with a status column, constrained to pending, processing or done. Producers insert pending rows and commit straight away. Each worker loops: it claims the oldest pending row with SELECT … ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED, does the work, marks it done and commits, which also releases the lock. If nothing is free, it sleeps briefly and polls again.”

Why SKIP LOCKED instead of plain FOR UPDATE?

“With plain FOR UPDATE, every worker queues up behind the same locked row, so only one is ever busy. SKIP LOCKED makes rows other workers have locked invisible, so each worker takes a different row at the same time, and when nothing is free it returns zero rows immediately instead of blocking.”

How do you process the queue twice as fast, and why is that safe?

“Add more workers; that’s horizontal scaling. It’s safe because each row is locked from the claim until that job’s commit, so only one worker can hold it, and the others skip it rather than wait. I tested two workers on 46 orders and got zero duplicates, with one taking the even ids and the other the odd ones. Eventually the database itself becomes the bottleneck.”

What happens if every pending row is locked?

“The query returns zero rows immediately. It doesn’t wait and doesn’t go back to a locked row. The worker treats that as ‘nothing to do’, commits to close the empty transaction, sleeps, and polls again.”

Why commit when the query found nothing?

“The driver opened a transaction for the SELECT. If I don’t end it, the worker sits ‘idle in transaction’ for as long as the queue is empty. That stops Postgres cleaning up old row versions and gets killed by idle-transaction timeouts. The commit doesn’t save anything; it just closes the transaction.”

A worker is killed with kill -9 after claiming a job. What happens?

“The process can’t clean up, but it doesn’t need to. Postgres sees the connection drop and rolls back the open transaction, which releases the lock. The job is still pending, so another worker claims it. No job is ever lost, so the queue gives at-least-once processing.”

Then why isn’t that enough for a trading engine?

“Because the side effect isn’t in the transaction. If the worker sent the order to the broker and then died before committing, the job goes back to pending and the next worker sends it again, so I buy twice. At-least-once plus retries means duplicates. The fix is an idempotency key: a unique client order id the broker remembers, so a repeat is recognised and ignored. That gives effectively exactly-once.”

At-most-once vs at-least-once vs exactly-once?

“At-most-once never repeats but can lose work. At-least-once never loses work but can repeat it after a failure. Exactly-once is what you want, and in practice you build it from at-least-once delivery plus idempotent processing, so a repeat has no extra effect.”

Pull or push: how do your workers get jobs?

“Pull. Each worker polls the table, and no coordinator assigns jobs. That keeps it simple and fault-tolerant: if a worker dies, the others just keep pulling. The cost is some empty polls; LISTEN/NOTIFY could add a wake-up signal if latency mattered.”

Why must the producer commit before it logs “new order”?

“Until it commits, the row is invisible to workers, and a crash or Ctrl+C rolls it back. I saw 15 orders printed and none saved. Committing first means every log line describes something that really exists.”

You see sessions stuck in idle in transaction. What do you do?

“Find them in pg_stat_activity; they’re holding locks and blocking cleanup. Kill them with pg_terminate_backend(pid), which rolls back their transactions, so committed data is safe. To prevent it, set idle_in_transaction_session_timeout and make sure every code path commits or rolls back.”
